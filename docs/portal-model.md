# 身份、门户和权限的分阶段拆分

## 已落地：同一前端工程中的门户上下文

右上角切换身份显示姓名、所属组织和角色，按所属组织与角色合并选项，每组只显示一人，优先保留当前选中身份；完整人员目录不变。
客户显示客户中心及当前客户名称；伙伴显示合作伙伴中心及当前伙伴名称；
所有 SmartX 内部职责显示服务管理中心及北京志凌海纳科技有限公司。
组织名称来自当前主数据，失效身份不回退为内部身份。

门户定义集中在 `apps/web/site/lib/portal-context.ts`。
系统管理员可见全部四个模块；项目经理（本任务所指 PMO）可见服务请求和服务目录；其他员工、客户和合作伙伴仅可见服务请求。
现有服务目录页面包含维护功能，因此暂不直接暴露给外部身份；申请表内的服务选择保留。
切换身份返回请求首页、关闭弹窗、重置详情组件，已保存的业务记录保持不变。
合作伙伴中心不提供新建服务请求，保存层也拒绝其新建记录。客户中心创建时隐藏客户选择项，自动绑定当前身份所属客户，联系人默认选择当前用户本人，可从该客户下的联系人中修改；保存层拒绝跨客户创建。内部身份保留客户选择项。

## 下一阶段：独立路由和权限配置

按 staff、customer、partner 分离入口和页面组织，共享基础组件。
建立用户到组织的成员关系，成员关系指定身份类型和可进入的门户，角色单独分配。
角色授权使用模块、操作、数据范围三个维度；同一组织多角色初期采用允许权限并集。
平台跨组织能力另行定义，不从门户名称或前端路径推导授权。

本次没有建立独立路由、角色配置后台或服务端鉴权。当前目录中的身份仍是演示身份，
浏览器本地存储仍为演示数据集。已增加本地记录访问规则：系统管理员和项目经理看全部，其他人员仅看自己创建或自己是内部/外部协作人的记录。新请求保存不可更改的创建人编号；旧请求只有创建人姓名时，必须能唯一匹配人员目录，否则仅管理员和项目经理可见。客户身份还可查看请求联系人编号为本人的记录；同公司其他联系人不会因此获得访问权。列表读取与保存均使用相同规则，保存时检查数据库中的原记录，不能通过自行添加协作人或篡改创建人取得访问权。外部协作人可选择本客户联系人及启用合作伙伴的启用用户。
引入真实账户前必须实现服务端成员关系校验、操作权限及数据范围过滤。
合作伙伴可服务哪些客户需由明确授权关系决定，不能仅按伙伴角色开放全部客户。

## 部署拆分条件

继续使用一个前端工程；出现员工端内网要求、独立登录策略或独立发布团队后，再拆部署。
