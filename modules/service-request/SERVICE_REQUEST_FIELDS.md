# 服务请求对象字段表

本文件是第一版本地原型中 `ServiceRequest`、`ServiceRequestItem` 与 `ServiceRequestBusinessObject` 对象的字段单一事实源。页面、表单、接口、数据库和测试数据实现时，应使用本文件中的名称、类型、状态与校验规则。

界面文案统一使用“服务申请”，代码中的主对象名称使用 `ServiceRequest`。核心流程固定为：

```text
草稿 → 待评估 →〔待审批：仅特批路径〕→ 待确认 → 待受理 → 已转工单
```

内部评估和必要特批先完成，再向客户发送服务范围、计费与客户资产使用概览；概览不展示内部特批信息。客户确认后冻结相应额度，成功后进入待受理。PMO 执行“受理并生成工单”后，申请阶段结束。排期、交付准备和执行由工单承载。

## 申请与业务对象关联（ServiceRequestBusinessObject）

业务对象不是服务申请的必填字段。一个申请可以不关联业务对象，也可以关联同一客户下的多个业务对象，因此使用独立关联对象，不在 `ServiceRequest` 上保存单个 `businessObjectId` 或 ID 数组。

| 标准字段名 | 中文名称 | 类型 | 创建必填 | 来源 | 规则与说明 |
| --- | --- | --- | --- | --- | --- |
| `serviceRequestBusinessObjectId` | 关联 ID | UUID / ID | 系统 | 系统生成 | 内部主键，全局唯一 |
| `serviceRequestId` | 服务申请 ID | ServiceRequest ID | 系统 | 系统关联 | 必须引用一条存在的服务申请 |
| `businessObjectId` | 业务对象 ID | BusinessObject ID | 是 | 申请人选择 | 必须引用一条存在且属于申请客户的业务对象 |
| `businessObjectCodeSnapshot` | 业务对象编码快照 | String | 系统 | 业务对象快照 | 创建关联时复制 `businessObjectCode` |
| `objectNameSnapshot` | 对象名称快照 | String(120) | 系统 | 业务对象快照 | 创建关联时复制 `objectName` |
| `createdBy` | 创建人 | User ID | 系统 | 系统记录 | 不可编辑 |
| `createdAt` | 创建时间 | DateTime | 系统 | 系统记录 | ISO 8601，展示时按用户时区格式化 |

同一申请下的 `businessObjectId` 必须唯一。提交申请时允许关联数量为 `0..N`；已经关联时，所有业务对象都必须属于申请的 `customerId`。

## 编码规则

| 对象 | 编码格式 | 示例 |
| --- | --- | --- |
| 服务申请 | `SR-{序号}` | `SR-001` |

序号默认使用三位，从 `001` 开始递增；超过 `999` 后自然扩展位数。编号仅由系统生成，前端、接口调用方和导入流程均不得自行指定或修改。数据库内部关联统一使用对象 ID，不使用展示编号作为外键。

## 对象关系

```text
Customer
└── ServiceRequest
    ├── Contact
    ├── ServiceRequestBusinessObject × 0..N
    │   └── BusinessObject
    └── ServiceRequestItem × 0..N（提交时 1..N）
        └── ServiceCatalog
```

- 一个服务申请必须且只能属于一个客户。
- 联系人必须与申请选择的客户一致。
- 业务对象可不选，也可多选；已选业务对象必须全部属于申请客户。
- 草稿允许零个子项，提交和后续状态下必须拥有至少一个有效子项。
- 允许多个子项引用同一服务目录，以区分不同范围；每个子项独立保存自己的参数、材料及可选业务对象。
- 服务目录或业务对象停用、修改后，不改变已经保存的申请快照。

## 状态流转（完整目标流程）

| 当前状态 | 操作 | 执行角色 | 目标状态 | 前置条件 |
| --- | --- | --- | --- | --- |
| 草稿 | 编辑并分项保存 | 申请人 | 草稿 | 可缺字段或材料；创建不等于提交 |
| 草稿 | 整单提交 | 申请人 | 待评估 | 基本信息完整；至少一个有效申请项；每项必填参数、材料齐全；关联对象如存在则必须有效 |
| 待评估 | 完成评估，正常依据充足 | PMO | 待确认 | 记录评估范围、工作量、依据并核对客户服务概览；内部发起须先关联有效服务依据 |
| 待评估 | 申请特批 | 销售 | 待审批 | PMO 记录缺口；销售补充申请原因和责任归属 |
| 待审批 | 审批通过 | 特批审批人 | 待确认 | 保留审批记录，核对服务概览；不向客户展示内部特批细节 |
| 待审批 | 审批拒绝 | 特批审批人 | 待评估 | 审批记录保留“已拒绝”，重新评估或由 PMO 取消 |
| 待确认 | 确认概览并处理额度 | 客户确认、系统处理 | 待受理 | 确认范围、计费和客户资产占用；需要冻结的额度须冻结成功 |
| 待受理 | 受理并生成工单 | PMO | 已转工单 | 核查承接条件和服务依据；原子创建全部工单，不要求先排期 |
| 未转工单 | 不再继续，取消请求 | PMO | 已取消 | 记录原因并处理已冻结额度；不删除已发生的审批记录 |

状态枚举为：草稿、待评估、待审批、待确认、待受理、已转工单、已取消。普通路径跳过待审批。审批拒绝不保留在待审批，不覆盖此前的拒绝记录。

额度冻结失败时保留待确认，并明确展示“已确认，额度待处理”；不能让客户重复确认。业务对象是环境范围，服务依据是资产/权益/合同或有效特批，两者不可混同，业务对象仍允许零个或多个。

## 阶段一致性规则

- 待审批不要求已经取得客户确认；正式客户确认在内部评估及必要特批之后。
- 待确认及之后必须有有效评估结果和服务依据；客户可见概览只显示其应确认的范围、计费和自身资产使用情况。
- 待受理必须有客户确认及有效依据，需要额度冻结时须冻结成功。
- 已转工单必须有受理人、受理时间和生成关联。申请单不保存工单排期。
- 本版可操作页面只实现草稿至待评估，后续阶段是目标规则，并非已经接入的真实审批能力。

## 工单生成一致性

- 受理并生成工单必须在一个数据库事务中完成：创建一个服务项目、按申请子项逐一创建工单、写入受理记录及关联和更新申请状态。
- 任一服务项目、工单或关联写入失败时，申请仍保持 `待受理`，不得留下部分受理或生成结果。
- 对同一 `serviceRequestId` 重复发起生成时，应返回已有服务项目和工单，不得重复创建。
- 工单继承对应申请子项的服务目录快照、确认后的 `assessedQuantity` 和服务方式；生成后再由工单安排时间、核查交付就绪条件和推进执行。

## 删除与历史规则

- 仅 `草稿` 状态可删除；删除申请时一并删除其未提交子项和业务对象关联。
- 已提交申请不得物理删除。第一版通过保留业务记录和普通活动日志满足演示追溯，不提供不可篡改审计保证。
- 客户、联系人、业务对象或服务目录被申请引用后，不因上游记录停用或修改而改变历史申请内容。

## 第一版实现边界

- 仅支持本地创建与处理，不连接 CRM、客户中心或其他外部入口。
- 目标流程为 PMO 评估、必要内部特批、客户确认、额度处理、PMO 受理并生成工单；排期归工单模块。
- 当前本地站点支持草稿创建、申请详情、1..N 申请项、弹窗填写申请项基础字段、保存后在申请详情页补充材料、版本上传下载、整单校验提交至待评估。其余流程尚未提供可操作页面。
- 本版不实现合并、暂停、撤销、评估退回操作、重新打开或多级特批；特批拒绝回评估和 PMO 取消已纳入上述目标流程。
- 不实现外部额度系统、SLA、通知或自动排期；额度与特批记录均保存在本地。
- 活动记录由 `activity-log` 模块旁路保存，不在本对象中复制状态历史列表。

## 本地申请资料版本（2026-09-07）

本节覆盖旧版“创建必填”与固定两项约束：基本信息和申请项资料在整单提交时校验，保存草稿允许不完整。完整实现说明见 [REQUEST_ITEM_MATERIALS.md](./REQUEST_ITEM_MATERIALS.md)。

- 安装类目录默认要求产品版本类型、产品版本号和正整数节点数。目录可调整哪些参数显示且必填。
- 目录申请配置是独立对象，不修改服务目录计价字段。材料要求含名称、填写说明、是否必填和模板；模板可上传替换。
- 每个申请项保存目录申请配置快照、参数、需求说明、可选多个业务对象和各材料的文件版本。
- 申请项状态“待完善 / 已完整”根据必填内容计算，不是审批状态。
- 本地原型将关联关系存为申请项的 ID 数组，逻辑上仍是多对多关系；正式数据库可采用独立关联表。请求级业务对象可由各项去重汇总。
- 请求编号在本地采用时间标识加随机后缀以避免刷新重号，与上方未来统一流水号方案分开。
- 本地原型使用浏览器 IndexedDB 同事务保存请求及文件字节；不上传远端。清除浏览器站点数据会丢失本地资料。
